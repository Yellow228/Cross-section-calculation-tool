# 一维推算「混合流」实现审查：与 HEC-RAS 的差距

> 对象：本次 PR #25 新增的混合流两遍法（`hydro1d.py` 第 589–720 行）
> 日期：2026-10-13　｜　性质：代码阅读 + 解析算例验证（探针用完已删）

---

## 一、结论（先说结果）

**混合流这部分是本次更新里最大的一块新代码（+588 行里占大头），但它的核心机制
"比力合并水面线"在物理上是错的，而且整个算法框架与 HEC-RAS 的混合流算法
有本质区别。当前实现不是"能用的混合流求解器"，更像是"把缓流、急流各推一遍
再粗糙拼接"。**

三个层面的问题：

| 层面 | 问题 | 严重度 |
|---|---|---|
| **判据错误** | 用「单断面比力 M 的大小」决定取缓流还是急流，物理依据不成立 | **P0（致命）** |
| **框架错误** | 两遍各自独立推、失败即 NaN 级联，没有 HEC-RAS 的"控制断面"机制 | P1 |
| **算法缺环** | 起推水位仍是 design_level（非正常水深边界）、临界水深回退是空实现 | P1/P2 |

---

## 二、核心隐患一：比力合并判据是错的（P0）

### 2.1 代码做了什么

混合流最后一步（`hydro1d.py:692-718`）：

```python
M_sub = calculate_specific_force(sec, z_sub, Q, ...)   # 缓流解的比力
M_sup = calculate_specific_force(sec, z_sup, Q, ...)   # 急流解的比力
if M_sub >= M_sup:
    res_levels[i] = z_sub        # 取缓流
else:
    res_levels[i] = z_sup        # 取急流
```

### 2.2 为什么这是错的

比力函数 `M(h) = A·ȳ + Q²/(gA)` 是**关于水深 h 的 U 形曲线**——
在 `h < h_c`（急流区）**单调递减**，在 `h > h_c`（缓流区）**单调递增**，
最低点在临界水深 `h_c`。

我用矩形宽渠（b=10, Q=50, q=5, h_c=1.366）算了 M(h) 的形态：

| 水深 h | 流态 | M(h) |
|---|---|---|
| 0.20 | 急流 | **127.6** |
| 0.30 | 急流 | **85.4** |
| 0.40 | 急流 | 64.5 |
| 1.37（临界） | — | 28.0 |
| 1.50 | 缓流 | 28.2 |
| 3.38 | 缓流 | **64.5** |

**M 的大小不区分流态方向**：急流水深很小（0.2 m）时 M 可以高达 127，缓流水深很大
（3.38 m）时 M 也可以回到 64。所以「M_sub >= M_sup 就取缓流」这个规则
**没有物理意义**——它只是在比谁离临界水深更远。

具体反例：缓流解 1.2 m（M=28.4）对比急流解 0.25 m（M=102.2），
`M_sub < M_sup`，代码会**取急流**——但正确的物理结果应该是缓流（该处是水跃下游）。

### 2.3 正确的水跃判据是什么

水跃（hydraulic jump）发生在**两个相邻断面之间**，不是单个断面上。
正确判据是**比力守恒（共轭水深）**：

```
急流侧水深 h1 和缓流侧水深 h2 满足  M(h1) = M(h2)
```

即：先在水跃上游用急流推、下游用缓流推，找到 `M(上游) = M(下游)` 的那个
**断面位置**（水跃位置），而不是在每个断面单独比 M 大小。

**代码把"断面间的比力守恒"误写成了"断面内的比力大小比较"。** 这是方向性错误。

## 三、核心隐患二：两遍法没有"控制断面"机制（P1）

### 3.1 HEC-RAS 怎么做混合流

HEC-RAS 的 Mixed Flow Regime 不是"缓流推一遍 + 急流推一遍再拼接"，而是：

1. 逐断面计算临界水深；
2. 找出所有**控制断面**（critical depth 的位置——水跃、跌水、堰、收缩段等）；
3. 以控制断面为界，把河段**切成若干子段**；
4. 每个子段内部是纯缓流或纯急流，**独立求解**，子段之间用比力/能量关系衔接；
5. 水跃位置由 `M_upstream = M_downstream` 精确求解。

关键在**第 2、3 步**：控制断面是求解的"锚点"，不是事后拼接。

### 3.2 代码怎么做

代码是「两遍独立推」：

- 第一遍缓流：从下游边界推到上游，**遇到第一个无解的段就停**（后续全 NaN）；
- 第二遍急流：从上游边界推到下游，**同理**；
- 然后按断面逐个「谁有解取谁」，都有解就比 M 大小。

**没有任何"找控制断面"的概念。** 所以：

- 实测合成水跃算例（陡坡→缓坡，必然产生水跃）：
  结果水位线 `11.219 / NaN / 7.109 / 5.719`——**中间 S2 直接 NaN 断掉**，
  且 S4 处居然是**急流（Fr=1.186）**，而水跃下游物理上必须全缓流。
  **整条线物理不自洽。**

- 真实工程强制 `auto` 后：每条线只多救回 1 个断面，中间仍留洞
  （因为两遍各断在失败点，中间那段两边都够不着）。

### 3.3 一句话

**HEC-RAS 混合流的本质是"以控制断面为锚点分段求解"，代码的本质是"两条独立水面线
在失败处硬拼"。两者不是同一件事。**

## 四、核心隐患三：算法缺环

### 4.1 起推水位仍是 design_level，不是正常水深边界

`hydro1d.py:531-541`：起推水位优先取 `design_level`，**只有 design_level 是 NaN 时**
才用 `compute_normal_depth` 兜底。

但 `design_level` 是我 10-09 就定位过的：由 H~Q 曲线**外插**得到，可能高于岸顶、
且相邻断面的正常水深之间不自洽。**正常水深函数做了，但语义没落地**——
它只是"没填设计水位时的兜底"，不是真正的边界条件。

### 4.2 "回退临界水深"是空实现（注释骗人）

`_secant_detail` 的 docstring 写：
> "当超出迭代次数不收敛时，**回退为临界水深**尝试继续推进"

但实际代码（`hydro1d.py:256-259`）：

```python
if not converged:
    exhausted = True
    x_new = float('nan')      # 直接 NaN，没有回退
```

- `fallback_to_critical` 恒为 `False`（第 254 行）；
- 传入的 `z_crit` 参数**在函数体内从未被使用**（只在签名出现）；
- 外部那句 `elif Z_up < Z_crit or d.get("fallback_to_critical")` 里，
  `fallback_to_critical` 永远是 False，是个死条件。

**"回退临界水深"这个设计从未实现，docstring 是残留的设想。**
（注：真回退临界水深本身也有争议——那会伪造解，10-09 我建议的是"别回退"。
所以这里的正确做法是**删掉误导性注释**，而不是补上回退。）

### 4.3 死代码与不可达分支

- `_bisect_detail` 已被生产代码弃用，只剩测试在用；
- `_secant_detail` 把 `clipped`/`at_lower`/`at_upper` 硬编码 False，
  导致 `_hydro1d_warnings` 里「贴边」告警分支**永远不可达**（10-07 的成果被废）。

## 五、与 HEC-RAS 的逐项对照

| 环节 | HEC-RAS 混合流 | 本次实现 | 差距 |
|---|---|---|---|
| 流态判定 | 逐断面算临界水深，自动定位控制断面 | 只有用户手选 regime（默认缓流） | **缺控制断面识别** |
| 求解策略 | 以控制断面为界**分段**求解 | 缓流/急流各推一遍、失败即断 | **本质不同** |
| 水跃处理 | `M_up = M_down` 精确求水跃位置 | 单断面比 M 大小 | **判据错** |
| 边界条件 | 显式指定（正常水深/已知水位） | 用 design_level 起推 | **缺边界语义** |
| 求根失败 | 明确报错、不伪造 | 返回 NaN（这步是**对的**） | 已对齐 ✓ |
| 局部损失/α | C=0.1/0.3、α 按 K 加权 | 同 | 已对齐 ✓ |

**总评：糙率、α、局部损失这些"单断面水力学"部分已经对齐 HEC-RAS；
但"水面线怎么连起来"——也就是混合流的核心——没有对齐，而且当前的做法物理上不成立。**

## 六、建议

### 短期（先止血，不改算法）

1. **别让用户以为"auto 就是混合流求解"**：当前 auto 会跑这个物理上不成立的
   比力拼接，结果（如上面的 S4 急流、中间 NaN）**看着是数值、实际是错的**。
   至少在界面上明确标注"混合流为实验性，结果仅供参考"，或默认仍走纯缓流。
2. **删掉 `_secant_detail` 里"回退临界水深"的误导性 docstring**，以及
   `fallback_to_critical` 这个死字段、死条件。
3. **删掉 `_bisect_detail` 死代码**，或把它的"贴边"诊断迁移到割线法（别让
   10-07 的成果静默失效）。

### 中期（真正对齐 HEC-RAS，需设计）

4. **实现控制断面识别 + 分段求解**：这是混合流的正确框架。量级约是重写
   `compute_hydro1d_profile` 的混合流分支，不是小改。
5. **水跃用共轭水深（比力守恒）定位**，替换现在的"单断面比 M 大小"。
6. **把边界条件做实**：起推断面用正常水深（或用户指定水位），不再用 design_level。

### 关键前提

**在动 4/5 之前，务必先用解析算例把预期结果钉死**——比如矩形宽渠的水跃
（已知 q、已知陡/缓坡，跃后水深有解析解），把"代码输出 vs 解析解"做成回归测试。
现在 `test_mixed_flow` 只断言 `len(levels)==4`，**完全不看数值**，这就是为什么
上面的水跃算例能跑出物理错误的结果、测试却全绿。

> 一句话：**这次混合流的代码量很大，但方向没走对。核心的"比力合并"判据
> 物理上不成立，整个框架与 HEC-RAS 的"控制断面分段求解"是两回事。
> 建议先止血（标注实验性 + 清理死代码），真正的混合流要按控制断面框架重做，**
> **且必须先用解析算例锁住正确结果再动工。**
